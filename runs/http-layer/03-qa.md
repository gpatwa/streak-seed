## Precondition 1 — the clock guard (carried from `runs/greenfield/08-security.md` §4)

**Probe script:** `probe-clock-guard.mjs`, 92 independent assertions against the real `dayIndex`, `logCompletion`, `listHabits` — not a re-run of C1–C10/H1–H3, a superset with new input classes.

**Part 1 — direct adversarial battery on `dayIndex()` (41 must-throw + 10 must-succeed cases).**
Beyond the spec's own table, I specifically targeted coercion bypasses, since the guard's safety depends entirely on the `typeof`/`instanceof` gate running *before* any arithmetic:

- Objects with a **throwing `valueOf`/`toString`/`Symbol.toPrimitive`** — confirmed these methods are **never invoked**; the type gate rejects on `typeof` alone, before any implicit coercion could occur. (This is the correct design — an attacker-controlled coercion hook is a classic bypass vector, and this guard has no path that would trigger one.)
- Boxed primitives (`new Number(...)`, `new String(...)`) — rejected, `typeof` is `"object"` for both.
- `BigInt`, `Symbol`, bare functions — rejected.
- A **duck-typed Date-like object** (`{ getTime: () => ... }`, not `instanceof Date`) — rejected. Confirms the guard isn't fooled by shape, only by real type.
- `Number.MAX_SAFE_INTEGER` (9.007e15) — just above the 8.64e15 boundary — throws, as it must.
- `-0`, fractional epoch ms, `Number.MIN_VALUE` — all succeed correctly (guard is not over-tight); `-0` is harmless because `Set` uses SameValueZero equality (`-0` and `0` are the same member).
- A `Date` **subclass** and a **Proxy-wrapped `Date`** — both accepted via `instanceof`, confirming the type gate isn't brittle to legitimate Date-like constructions.

One genuine oddity, not a guard defect (see Finding 2 below): `dayIndex(new Proxy(new Date(x), {}))` throws, but via a **native engine `TypeError` ("this is not a Date object.")** fired inside `now.getTime()`, not the guard's own controlled message. Still `TypeError`, still pre-mutation (see below), still unreachable from HTTP.

I also independently reproduced the spec's own "[probe] Correction" claim: `new Date(MAX_TIME + 1000).getTime()` is **already `NaN`** at construction (confirmed empirically), which is *why* the raw-number form of that boundary is the only one that matters for C7 — the Date-wrapped form was never going to slip past a naive check in the first place.

```
=== PART 1 ===  41/41 must-throw pass, 9/10 must-succeed pass (Proxy case — see Finding 2)
```

**Part 2 — pre-mutation + zero-collateral-damage, for 16 distinct adversarial `now` values** (the spec's own H1/H2 only exercise two: `new Date("garbage")` and `8.64e18`). For each value I drove it through `logCompletion(victim, target, badNow)` with a **sibling habit for the same user** and a **habit for a different user** already seeded, and asserted all five of: throws `TypeError` · target habit's streak/date unchanged · sibling habit unchanged · other user's habit unchanged · audit-event count unchanged · **and** that a subsequent valid call recovers normally (no permanent corruption). All 16 passed, plus 6 more via `listHabits`.

```
PASS logCompletion(victim, target, null) throws pre-mutation, zero collateral damage
PASS logCompletion(victim, target, object with throwing valueOf) throws pre-mutation, zero collateral damage
PASS logCompletion(victim, target, 8.64e18) throws pre-mutation, zero collateral damage
... (16/16)
PASS listHabits(reader, ...) throws, subsequent valid listHabits returns both habits (6/6)
```

**HTTP-level: is there any channel a client can use to reach `now` at all?** I re-derived this myself rather than trusting the spec's own S15 regex:
- Grepped `server.js`: zero `new Date(` calls anywhere in the file; the only two service call sites are literally `logCompletion(userId, habitId)` and `listHabits(userId)` — fixed arity, confirmed by regex extraction, not just presence-testing.
- Grepped for every `req.headers` read in the file: **the only header ever read is `x-user-id`.**
- Live HTTP attempts to smuggle a clock value through **every plausible channel**: 6 header names (`X-Now`, `X-Date`, `X-Timestamp`, the real HTTP `Date` request header, `If-Modified-Since`, `X-Forwarded-*`), 12 body field names (`date`, `now`, `timestamp`, `today`, `clock`, `epoch`, `ts`, `time`, `utcNow`, `serverTime`, `day`, `dayIndex`), and query-string params — all ignored; the completion route's `changed` flag never flips based on any of them, which is a behavioral proof, not just an absence-of-error check.

**Verdict on precondition 1: holds.** No input — type-confused, boundary, astronomical, or coercion-based — reaches a `Set` without the guard rejecting it first, and no HTTP channel can reach the clock argument at all.

## Precondition 2 — the non-oracle (foreign vs. fake `habitId`)

**Probe script:** `probe-http.mjs`, run against the real server via `node:http` (not `fetch`), specifically so I could read `res.rawHeaders` — the **literal wire order and casing**, which `fetch`'s `Headers` object normalizes/sorts before you ever see it. (The shipped S17 test compares `[...headers.keys()].sort()`, which is what the spec's own prose promises — "the sorted list of response header names" — so this isn't a gap in S17, but I wanted the stronger, unsorted check independently.)

```
PASS status: foreign 404 === fake 404
PASS body bytes: raw byte-for-byte identical
PASS content-length header value identical (27 / 27)
PASS raw wire header NAME+ORDER identical (excl. Date/Connection) — 
     both: ["content-type","cache-control","content-length"]
PASS no transfer-encoding:chunked on either
PASS access-log line byte-identical apart from duration
PASS prober accrued zero audit events
PASS victim accrued zero NEW events from the prober's probes
```

**Garbage-id sweep, widened beyond the shipped S19 (4 ids) to 31**, including: `%20`, `__proto__`, `constructor`, `prototype`, `hasOwnProperty`, a 2 KB string, case/format variants (`HABIT_1`, `habit_01`, `habit_1.0`, `habit_-1`, `habit_1e0`), dot-segments (`..`, `%2e%2e`), a null byte (`%00`), encoded `喝水八杯` and `<script>x</script>`, an encoded SQL-injection-shaped string, prototype-pollution-flavored keys (`toString`, `valueOf`, `__defineGetter__`), and an encoded backslash. **All 31 produced the byte-identical 404.**

**Enumeration sweep widened from the shipped `habit_1..20` to `habit_1..50`** with mixed real ownership across three users — all 50 byte-identical to the fake-id response.

**A boundary the spec explicitly calls out but doesn't test:** Node's own request-line size limit. I confirmed it's uniform by *length*, not by *content* — a fully-fake 20,000-char id and a 20,000-char id **built by padding a real, existing habitId** both hit the same wall:

```
20000-char fake id in URL path:                      431 (empty body, from Node itself)
15000-char padding + a REAL prefix habitId:           404 {"error":"habit not found"} (under the 16KB limit)
```

No oracle at that boundary either — it's decided purely by byte length before the app ever sees the id.

**Verdict on precondition 2: holds**, across every axis I could measure — status, raw body bytes, content-length, literal wire header order, absence of chunked-encoding fallback, access-log line, and audit-event count — over a substantially wider adversarial-id space than shipped.

## Other invariants, probed over real HTTP

**§5 idempotency** (`probe-http.mjs`, section D): 3× same-day `POST .../completions` → 1st `changed:true`, 2nd and 3rd `changed:false`; all three `habit` objects `JSON.stringify`-identical; **exactly one** `habit.completion_logged` audit event; all three responses `200` (never `409`).

**§4 cross-user isolation** (section E): after **5** failed cross-user log attempts, the victim's habit is untouched (`currentStreak:0`, `lastCompletedDate:null`), neither user's list contains the other's habit, and the attacker's audit trail contains **only** their own legitimate `habit.created` event — zero `habit.completion_logged` leaked from the failed attempts.

**§6 no sensitive content in logs** — this is the one place I deliberately did **not** reuse the in-process test harness. I spawned `node src/server.js` as a genuine separate OS process (`probe-real-server-logs.mjs`), which is the only way to exercise the **default** `log = process.stdout.write.bind(process.stdout)` binding — every test in the shipped `test/server.test.js` constructs the server with an injected `log` sink (`before()`, line 13), so the real default path is never exercised by the suite at all. Against the real process, with 7 adversarial habit names including two **CRLF/log-injection attempts** (`"line1\nPOST /admin/delete 200 0ms\nline3"`, `"line1\r\nGET /secret 200 0ms"`) and a marker user id:

## Assessment of the engineer's 5 deviations

1. **Explicit `content-length` header.** Verified live: present, byte-accurate (`Buffer.byteLength` matches the wire value), and — critically for the non-oracle — identical between foreign and fake responses, with no `transfer-encoding: chunked` fallback on either. **Necessary and correct**; it makes the spec's own "equal by construction" claim actually observable instead of vacuous.

2. **Raw string routing instead of `new URL()`.** I didn't take the stated rationale on faith — I diffed the two parsers directly on the paths most likely to disagree:

   ```
   raw="/habits/foo/../bar/completions"
     raw slice  -> "/habits/foo/../bar/completions"   (falls to generic 404, no route match)
     new URL()  -> "/habits/bar/completions"           *** DIVERGES *** (would match the route!)
   raw="/habits/foo\bar/completions"
     raw slice  -> "/habits/foo\bar/completions"        (one opaque segment, habitId = "foo\bar")
     new URL()  -> "/habits/foo/bar/completions"        *** DIVERGES *** (backslash→slash)
   raw="/habits/%2e%2e/completions"
     raw slice  -> "/habits/%2e%2e/completions"          (one opaque segment)
     new URL()  -> "/completions"                        *** DIVERGES *** (decodes AND collapses)
   ```

   This is a **real, substantial divergence**, not a theoretical one — `new URL()` would have silently reinterpreted `/habits/foo/../bar/completions` as a request for habit `bar`, and would have decoded-then-collapsed `%2e%2e` into an entirely different route. Neither would have broken the non-oracle itself (both still resolve through the same ownership-gated `logCompletion` path), but both would have made routing behavior depend on a parser's normalization rules rather than the wire bytes — exactly the class of surprise the spec's §2.4 "raw path segment, not decoded" contract is designed to rule out. **Deviation is justified, and the justification is now backed by a live diff, not just prose.**

3. **`MAX_BODY_BYTES` enforced for every route.** Verified live for `GET /health`, `GET /habits`, and an unmatched route — all three correctly `413` on a 9000-byte body. (One methodological note for transparency: my first attempt at this sent the oversized body via Node's `http` client without an explicit `Content-Length` on a `GET`, which makes the client fall back to chunked transfer-encoding; that variant gets rejected by **Node's own HTTP parser** before the request ever reaches `server.js` — confirmed by a `clientError` listener and a raw-socket capture showing a header-less, app-uncontrolled `400`. That's a client-library artifact, not a server defect. Every real client that sends a body — curl, browsers, `fetch` — sets `Content-Length` explicitly, so I redid the probe that way and got the claimed `413` cleanly.) Confirmed correct.

4. **Unmatched routes skip JSON parsing.** Verified: an unmatched route with a deliberately malformed body still returns clean `404 {"error":"not found"}`, never `400 invalid json`. Confirmed.

5. **`demo` script preserved.** Ran `npm run demo` myself; unchanged output, unaffected by the `server.js`/`package.json` changes.

All five deviations are real improvements or defensible, non-spec-violating choices; none change a documented status code, error phrase, or body shape.

## Findings

**1. (Real, minor, does not violate any invariant or precondition) — 413 path breaks the client's *next* request on a reused keep-alive connection.**

The 413 handler calls `req.destroy()` after the response is flushed (`sendAndDestroy`), which in Node also tears down the underlying TCP socket abruptly. I reproduced, deterministically, that a well-behaved client using a persistent connection (the HTTP/1.1 default — this is not an exotic client) gets the 413 response **fully and correctly** for the request that triggered it, but if that same client's connection pool reuses the now-dead socket for its **next, unrelated** request, that next request fails with `ECONNRESET`/`EPIPE` before ever reaching the server:

```
request 1 (oversized POST, keep-alive): 413 {"error":"payload too large"}   <- delivered correctly
request 2 (unrelated GET /health, same pooled socket): ECONNRESET socket hang up  <- never reaches server.js
request 3 (agent evicts the dead socket, retries fresh): 200 {"status":"ok"}      <- recovers
```

This does **not** violate §2.1's own promise ("never write to an already-destroyed response" — the 413 body is always delivered whole, confirmed) and does **not** touch any of the six safety invariants or either carried precondition — it's a connection-lifecycle side effect, not a data or oracle issue. Many HTTP clients (as shown in request 3) recover transparently on their next attempt; naive ones surface a spurious low-level error to whoever issued that unrelated call. Worth a follow-up (e.g., send `Connection: close` on the 413 response so well-behaved clients know not to reuse it, rather than destroying it silently), not a blocker for this slice.

**2. (Cosmetic, zero practical impact) — one exotic input bypasses the guard's own error message, not its safety.**

`dayIndex(new Proxy(new Date(x), {}))` passes the `instanceof Date` check, then `now.getTime()` throws a **native engine `TypeError`** ("this is not a Date object.") rather than the guard's designed message. It is still a `TypeError`, still thrown before any `Set` mutation (the ownership check in `logCompletion` runs first regardless, and `dayIndex` is called before any `days.add`), and it's unreachable from HTTP (fixed arity, confirmed above) — and even if it somehow weren't, the HTTP layer's catch-all swallows every message into `{"error":"internal error"}` regardless of content. No action needed; noted only for completeness since the probe battery specifically went looking for coercion/type-confusion bypasses.

---

## Verdict: **PASS**

Both carried preconditions — the clock guard's pre-mutation safety and the foreign/fake non-oracle — held against an adversarial input space substantially wider than the shipped test suite (92 clock-guard probes vs. 20 shipped; 31 garbage ids vs. 4 shipped; a 50-id enumeration sweep vs. 20 shipped; a genuinely separate spawned process exercising the untested default log path). All six safety invariants were independently re-verified over real HTTP, not re-read from the spec. All four gates reproduce exactly. All five deviations are justified — deviation #2 in particular is now backed by a concrete, live divergence rather than prior-art caution. The two findings above are real but narrow: one is a connection-lifecycle robustness nuance with no data or oracle impact, and the other is a single exotic input whose only consequence is a less-pretty internal error message that never reaches the wire. Neither weakens an invariant, neither reopens either carried precondition, and neither should block this slice.
