## 3. F-3 live Chromium verification — the load-bearing check

`01-impl.md`'s "zero sinks" conclusion for `require-trusted-types-for
'script'` is a **static-analysis prediction**, explicitly not verified live by
the implementer (out of that role's tool boundary, and assigned to QA by the
slice plan as success criterion 4 / Risk 1). This section is that
verification, run against a real Chromium, not re-derived from the source
table in `01-impl.md`.

### Method

No browser MCP tool is in my tool boundary either (Read, Write, Edit, Bash,
Grep, Glob only). Did it from Bash: Node 25's native `WebSocket` speaking the
Chrome DevTools Protocol directly over the debugging socket — no npm
install, no dependency added anywhere.

1. Started the app server on a non-default port, loopback-only (the source's
   own binding, unmodified):
   ```
   $ PORT=8743 node src/server.js
   streak-seed listening on 127.0.0.1:8743
   ```
2. Launched headless Chromium with a scratch profile, isolated from the real
   browser:
   ```
   $ "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
       --headless=new --disable-gpu --no-first-run --no-default-browser-check \
       --remote-debugging-port=9333 \
       --user-data-dir=<scratchpad>/qa-security-hardening/chrome-profile \
       about:blank
   ```
3. Wrote `<scratchpad>/qa-security-hardening/cdp-check.mjs`: connects over
   `ws://127.0.0.1:9333/devtools/browser/...`, creates a tab
   (`Target.createTarget`), attaches a session, enables `Page`, `Runtime`,
   `Log`, `Network`. Before any navigation, injects (via
   `Page.addScriptToEvaluateOnNewDocument`, so it runs before `boot.js`) a
   `securitypolicyviolation` collector on `document`, and a `window.__pwned`
   flag that a successful hostile-name execution would flip. Captures
   `Runtime.consoleAPICalled`, `Log.entryAdded`, `Runtime.exceptionThrown`,
   and `Network.responseReceived` headers for the whole session.
4. Exercised the real app end to end, not just a single load: empty state →
   seed one ordinary habit (`Drink water`) and one hostile-named habit
   (`<img src=x onerror=window.__pwned=true>`) via `fetch` against the real
   `POST /habits` route, same as a real client → reload → list state → hash
   navigation into the hostile habit's detail view → click the real "Log
   today" button (a real `POST /habits/:id/completions`) → hash-navigate to a
   nonexistent habit id (not-found state) → back to list.
5. At the end, read `window.__cspViolations`, the CDP `Log` entries, console
   messages, and exceptions; read the actual `content-security-policy`
   response header off the real `Network.responseReceived` event (not
   re-derived from source).
6. Ran a deliberate non-vacuity probe (below) to prove the check would have
   caught a real violation, not just the absence of one.
7. Killed Chromium and the server; confirmed both ports closed.

### Non-vacuity probe — proving the check would have caught a real violation

A collector that never fires proves nothing by itself — it could be silently
broken. Deliberately tripped a real Trusted-Types-guarded sink, *after* all
the real app states above had already been exercised cleanly:

```js
document.getElementById('app').innerHTML = '<b>trusted-types-probe</b>';
```

Result:

```json
{
  "threw": "TypeError: Failed to set the 'innerHTML' property on 'Element': This document requires 'TrustedHTML' assignment.",
  "appHtmlChanged": false
}
```

The assignment threw synchronously, `#app`'s HTML was provably unchanged
(`appHtmlChanged: false`), and CDP's `Log` domain recorded a `source:
"security"` entry with the browser's own enforcement text. Two independent
CDP channels (the in-page thrown exception and the `Log` domain) both
confirm the mechanism is live in this Chromium build, not merely a header
with no effect. Had any real client code touched an injection sink during
the five states exercised above, this is the exact signal it would have
produced — and it produced none until this deliberate, out-of-band probe.

One asymmetry worth recording rather than glossing over: `document`'s
`securitypolicyviolation` event listener (the one I injected via
`Page.addScriptToEvaluateOnNewDocument`) did **not** record this particular
violation — `window.__cspViolations` stayed `[]` even after the probe. The
CDP `Log` domain did catch it. This is a one-time observation about this
Chromium build's event-dispatch timing/scope for sink-level Trusted Types
violations (as opposed to policy-header violations like a blocked
`<script>` load, which the same listener does catch per the
`browser-client` security review's §2.2), not a defect in this slice — it
does not change the pass/fail call, since the `Log` domain and the thrown
exception both independently proved enforcement. Not worth crystallizing
into a permanent test: this is a browser-runtime-timing fact, not a property
of this repo's source, and the repo's test suite is explicitly
dependency-free with no browser runtime available to it (`LOCAL_COMMANDS`).

## 8. Crystallize what you prove

Two probes were run beyond re-confirming what `01-impl.md` already claims;
neither becomes a new permanent test, for stated reasons:

1. **§3's live Chromium session and its non-vacuity probe** (forcing an
   `innerHTML` write to prove the browser really enforces
   `require-trusted-types-for 'script'`, and that CDP's `Log` domain would
   catch a real violation). This cannot be crystallized into `test/`: it
   requires a real Chromium process, and `LOCAL_COMMANDS.md`/`CURRENT_MVP_
   STATUS.md` are explicit that this is a **dependency-free** Node suite with
   no browser runtime available to it. `C22` already is the permanent,
   cheap regression guard for the one part of this that *is* source-level —
   the CSP string containing the directive, byte-for-byte. What only a live
   browser can prove (that Chromium actually enforces it) is inherently a
   one-time-per-Chromium-version fact, not a property of this repo's source;
   summarized here, not landed as a test.

2. **§5's five-route/status-code header check.** Ruled out a hypothesis
   before writing anything: I initially assumed `S32`/`S32b` (one 201, one
   413) might leave a coverage gap for other status codes (400, 404) or
   routes. Reading `src/server.js` shows exactly three response-writing
   functions total — `sendStatic` (unaffected by F-4, pre-existing
   `nosniff`), `send`, and `sendAndClose` — and **every** JSON-producing
   branch in `handleRequest` calls one of the latter two, with the header
   map set unconditionally, no per-status or per-route branching inside
   either function. So `S32` (exercises `send()`) and `S32b` (exercises
