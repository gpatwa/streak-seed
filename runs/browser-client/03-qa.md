## 2. The escaping boundary — independent probe

Read `src/client/dom.js`, `render.js`, and the existing `test/client-dom.test.js`
/ `test/client-render.test.js` (C4/C11) first to understand the claimed
mechanism — a vnode representation with no `html` child kind, and `dom.js` as
the sole file touching the DOM, with every string child becoming a
`createTextNode`. Then wrote an **independent** probe script (not the
engineer's test file) exercising hostile names the existing suite does not
already cover, against the real `render.js` + `dom.js` pipeline, using a
hostile stub `document` that throws on `innerHTML`/`outerHTML`/
`insertAdjacentHTML`:

- `<script>alert(document.cookie)</script>` — a name that is pure `<script>`.
- `<img src=x onerror=alert(1)>` — the spec's own example, re-verified.
- `"><svg/onload=alert(1)>` — quotes/angle-brackets in an attribute-breakout
  position.
- `‮evil‬​normal<b>name</b> null` — Unicode bidi-override characters (RTL
  override U+202E, PDF U+202C, ZWSP U+200B) mixed with markup.
- `🔥‏mood<img src=x onerror=alert(2)>` — emoji + bidi mark + markup combined.

Result — all five: rendered through `HabitRow` and `HabitDetail`, mounted
against the hostile stub, **zero traps fired**, the name always appeared as
exactly one `createTextNode` call carrying the byte-identical string, and no
`setAttribute` call anywhere in the tree contained any part of the name.

```
[PASS] pure <script> name: text-node-present=true attr-leak=false trap-fired=false
[PASS] img onerror (spec example): text-node-present=true attr-leak=false trap-fired=false
[PASS] attribute-breakout quotes/angle-brackets: text-node-present=true attr-leak=false trap-fired=false
[PASS] unicode + RTL override: text-node-present=true attr-leak=false trap-fired=false
[PASS] mixed emoji + bidi + markup: text-node-present=true attr-leak=false trap-fired=false
```

**Proving the probe is non-vacuous (not just checking for absence of an
`alert`).** Made a scratch copy of `dom.js` (outside the repo, in the
scratchpad — never touched the real file) and mutated `create()` to assign
hostile string children via `el.innerHTML = ...` instead of
`createTextNode` — the exact regression this design exists to rule out. Ran
the same probe against the mutant:

```
[FAIL] pure <script> name: mount() threw: TRAP: innerHTML assigned
[FAIL] img onerror (spec example): mount() threw: TRAP: innerHTML assigned
[FAIL] attribute-breakout quotes/angle-brackets: mount() threw: TRAP: innerHTML assigned
[FAIL] unicode + RTL override: mount() threw: TRAP: innerHTML assigned
[FAIL] mixed emoji + bidi + markup: mount() threw: TRAP: innerHTML assigned
```

The trap fired for every case — confirming the probe (and by construction the
equivalent hostile-stub tests C4/C11 in the real suite) would catch a real
regression, not merely the absence of a firing `alert()`. Also ran the exact
C8 banned-token regex (from `test/client-static.test.js`) over the mutated
file as plain text: it flagged `innerHTML` on both the mutating line and the
explanatory comment above it — confirming the **static scan** independently
catches the same class of regression, as a second, source-text-level layer
distinct from the runtime DOM-API trap. Restored: the mutant lived only in
the scratchpad directory; the real `src/client/dom.js` was never modified.

**C4 genuinely asserts text, not just absence of alert.** Read `test/
client-render.test.js`'s `C4` closely: `assertSafeTree` walks the whole vnode
tree and asserts (a) the hostile name appears as a byte-identical **string
child** somewhere (`sawNameAsChild`), (b) no prop value anywhere contains any
part of it, (c) every `tag` is drawn from a small fixed allowlist, (d) no
vnode carries an `html`/`innerHTML`/`dangerouslySetInnerHTML` key. That is an
assertion about representation (text vs. markup), not about script execution
— consistent with what the independent probe above found by mounting through
a hostile DOM stub. Verdict: **the claim holds.**

**Banned tokens, independently grepped** (not just trusting C8's own pass):
`grep -rn` for `innerHTML|outerHTML|insertAdjacentHTML`, `\bDate\b`,
`console\.`, and `document\.title` across `src/client/` — zero matches for
all four, confirming the source is clean independent of the test harness.

**Sinks outside the DOM tree (§3.4 of the arch doc).** Confirmed by grep:
`document.title` is never written (stays the static `"StreakKeeper"` in
`index.html`); no `history.pushState` or query-string use anywhere in
`app.js`; `getUserId()` reads `localStorage` but the value is never passed to
`render.js`, never interpolated into a URL, and never rendered — verified by
reading `app.js` end to end (`userId` is used only as a `fetch` header value).

**The non-oracle.** Read `app.js`'s `renderDetail` and `handleLog`: both

UI, confirmed both statically (code read) and live (real HTTP 404 bodies).**

## 8. The manual browser check (`01-arch.md` §10, "Manual check (QA, not
automated)") — performed live, and it found a real defect

The arch doc's own test plan explicitly declines to automate this: "One pass
in a real browser: tab through the list (two stops per row, in order),
activate the log control with Space and confirm focus does not move, confirm
the live region announces once, and view a habit named with markup to
confirm it displays as literal text. Recorded in the QA artefact, not
asserted in CI." `02-impl.md` shows no evidence this pass was ever performed —
only the 81 automated tests and a synthetic Node-script check of the escaping
boundary appear there, no browser transcript. This is precisely the gap QA
exists to close, so it was run here, using the Claude Browser tool against
the real running server (`PORT=3933`, seeded with a hostile-name habit and
three ordinary habits via `curl`).

**Confirmed good:**
- The hostile-named habit (`<img src=x onerror=alert(1)>`) renders as
  **literal visible text** in a real Chromium DOM — screenshot and
  `get_page_text` both show the literal characters, no `alert` fired, no
  console errors, and a second normal habit rendered unaffected alongside it.
- Tab structure matches the spec: each row exposes exactly two interactive
  elements in DOM order — the name link (`href="#/habit/<id>"`) then the
  `Log today`/`Logged` button — confirmed via the accessibility tree for four
  seeded habits.
- The live region fires correctly and exactly once per successful log, with
  the right copy and correct pluralisation: `"Drink water logged for today.
  Current streak 1 day."`, `"Yoga logged for today. Current streak 1 day."`,
  `"Read logged for today. Current streak 1 day."`.
- `POST /habits/:id/completions` actually mutates and the UI reflects it: the
  button label swaps `Log today` → `Logged`, the streak figure updates.

**Confirmed broken — focus does NOT stay on the control after logging.**
Both `01-arch.md` §7.2 ("After logging, focus stays on the control. Nothing
steals focus — no toast, modal, or scroll-into-view.") and `04-ui.md` §4
("After logging, focus stays on the same control; nothing steals focus to a
toast, modal, or animation.") state this as a hard requirement. Live-clicked
the log control for three different habits, in both list view and detail
view, and checked `document.activeElement` immediately after each:

```
Click "Log today" for Yoga (list view)  -> activeElement: BODY (not the button)
Click "Log today" for Read (detail view) -> activeElement: BODY (not the button)
```

Reproduced twice, independently, in two different views. **Root cause,
confirmed by reading the code (not guessed):** every successful log calls
`render()` → `renderList()`/`renderDetail()` (`src/client/app.js`), which
calls `mount(root, ...)` (`src/client/dom.js`), and `mount()` unconditionally
does `parent.replaceChildren(create(vnode))` — a full teardown-and-rebuild of
the entire mounted subtree, including the button that was just clicked, on
*every* render, not just the row that changed. Per standard DOM behaviour,
removing the currently-focused element from the document moves focus to
`<body>`. `grep -rn "\.focus(" src/client/` returns nothing — there is no
code anywhere in the client that re-focuses the new button after a remount.
This is not "a toast steals focus" in the literal sense the spec's example
names, but the observable effect for a keyboard or screen-reader user is the
one the requirement exists to prevent: after every successful log, focus
context is lost and the user is dropped back at the top of the document,
needing to re-Tab down to find their place again. For a screen-reader user
this is worse than jarring — VoiceOver/NVDA would announce the page-level
landmark again, not "still on the button you just pressed."

This is a genuine, reproducible defect against an explicit, named
requirement in both the UX spec and the architecture doc, not a nice-to-have.
It was not caught by the 81 automated tests because — correctly, per the
arch doc's own reasoning — none of them use a real DOM with focus semantics;
the hostile-stub `document` in `client-dom.test.js` has no
`document.activeElement` concept at all. That is exactly why the arch doc
routed this specific check to a manual pass instead of CI, and exactly why
it needed to actually be run rather than assumed.

**Not added as an automated test.** Per the arch doc's own stated reason for
keeping this manual ("no browser automation is being added to a
dependency-free repo"), and because the repo's test architecture
deliberately has no DOM with focus semantics to assert against, writing a
regression test for this would mean introducing the exact dependency the
architecture rejected. Documenting it here, as the manual check specifies,
is the correct crystallization for this one — not a `test/` file.

## 9. The declared deviation — component handler params

`02-impl.md` declares one deviation: `HabitRow`/`HabitDetail`/
`LogTodayControl` gained optional trailing parameters (`onLog`,
`inlineErrorMessage`) beyond the single-argument signatures `01-arch.md` §2.3
tables. Read the rationale and checked it against the actual non-negotiable
it claims to preserve (`dom.js` as the *only* file touching the DOM):

- Verified `app.js` never calls `document.*` directly — `grep -n
  "document\." src/client/app.js` returns nothing; all DOM access goes
  through `byId`/`mount`/`setText` from `dom.js`. Had `render.js`'s
  components taken no handler, `app.js` would have needed
  `root.querySelector(...)` + `addEventListener` to wire clicks after
  mount, which would make `app.js` a second DOM-touching file — a real
  violation of a structural invariant the arch doc treats as load-bearing
  (§2.1: "the ONLY file that touches the DOM").
- The extra parameters carry **function references only** (`onLog`) or a
  **string already drawn from `COPY`** (`inlineErrorMessage`) — nothing that
  touches the DOM, reads it, or calls a DOM API. `render.js` remains a pure
  function of its arguments; passing a closure through untouched is not an
  impurity.
- The `on` prop threading exploits a mechanism the arch doc's own `dom.js`
  §3.3 already specifies (`on: {event: fn}`, function-only, `addEventListener`
  only) — this isn't a new escape hatch, it's the documented one, reached one
  layer higher up the call chain than the table implied.
- Confirmed the pure unit-test call sites still work with the handler
  omitted (`HabitRow(view)` with no second argument) — checked directly in
  `test/client-render.test.js` C1–C6, which call every component with 1
  argument and pass.

**Verdict on the deviation: sound.** It resolves a genuine tension in the
spec (single-arg table vs. "dom.js is the only DOM-touching file") in favor
of the rule that actually matters for the escaping boundary, without
weakening it. This is not where the focus-loss defect above lives — that
defect is in `dom.js`'s `mount()`/`replaceChildren` behavior and app.js's
render-triggering, which is unaffected by how the click handler got wired.

The other three undeclared-but-summarized deviations at the bottom of
`02-impl.md` were spot-checked and are minor and non-security-relevant:
`copy.js` carrying `days()`/`sr*`/`liveLogAnnouncement` alongside the 16
constants keeps every screen string in the one file C1 checks (consistent
with the arch doc's own stated goal); `ErrorNotice`'s `role="alert"` is
additive and already in `dom.js`'s `ALLOWED_PROPS`; and dropping a
404'd habit from `state.habits` client-side is consistent with §4.1's
"one source of truth" and does not introduce any new timing or branch
asymmetry between foreign and fake ids (both still resolve through the
identical `mapLogResponse`/`findHabit` path).

## 10. Gaps and residual risk (stated, not hidden)

- **The focus-after-logging defect (§8) is the one blocking finding.**
  Confirmed live, twice, in both list and detail view, with a code-level
  root cause identified. Recommend routing back to Implementation before
  Security/Release: the fix is almost certainly re-focusing the equivalent
  new button after a re-render triggered by `handleLog`'s success path (the
  habitId is known; `dom.js` would need a small addition, e.g. returning the
  mounted root or exposing a way to refocus by a stable key — this is an
  implementation decision, not QA's to make).
- **`__proto__` as a habit name** was exercised by the existing C4 test and
  is inert here because names only ever become `children` strings and
  `Object.entries`/plain-object literals in `render.js`, never a live object
  key assigned via bracket notation from untrusted input — confirmed by
  reading `render.js` end to end; no `obj[name] = ...` pattern exists
  anywhere in the client.
- **Unicode/bidi visual spoofing** is explicitly out of scope per arch doc
  §3.8, and the independent probe in §2 confirms it stays confined to the
  name's own text node (no structural escape) even with RTL override
  characters mixed with markup-looking text — consistent with the spec's own
  stated non-claim.
- **No regression test was added for the focus defect**, per the reasoning
  in §8 — the arch doc explicitly keeps this class of check manual and
  out of CI for a dependency-free repo. If the team ever adds a minimal DOM
  (jsdom or similar) for a future slice, this would be the first candidate
  for automation.

## Verdict: **FAIL**

Every automated gate is green (81/81, typecheck, build), the escaping
boundary is genuinely sound (independently probed with five hostile inputs
including two not in the existing suite, and the trap/scan were both proven
non-vacuous by mutation), the banned-token list is honored, copy is verbatim
byte-for-byte, all seven states render correctly, the non-oracle survives
the UI (confirmed live over real HTTP), the S24 widening is a genuine
widening not a weakening, and the static route is correctly locked down
(headers, traversal, no-user-data). The declared deviation (component
handler params) is sound engineering, not a compromise of the escaping
boundary.

However, the manual browser check that `01-arch.md` §10 itself calls
for — and that `02-impl.md` gives no evidence of having been run — surfaces
a confirmed, reproducible violation of an explicit, named interaction
requirement in both `01-arch.md` §7.2 and `04-ui.md` §4: **focus does not
stay on the log control after a successful log; it reverts to `<body>`**,
in both list and detail view, because `mount()`'s full-subtree
`replaceChildren` on every render tears down the just-clicked button and
nothing re-focuses its replacement. This is an accessibility regression
against a requirement the UX spec treats as load-bearing (the same section
that rules out toasts and modals stealing focus), not a cosmetic nit. It
should be fixed and re-verified with the same manual browser pass before
this slice proceeds to Security/Release.
