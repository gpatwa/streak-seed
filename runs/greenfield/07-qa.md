## 2. Invariant-by-invariant independent verification

### §1 — One server-side day boundary (mutual exclusion + client-authority)

**Probe A — brute-force sweep**, far beyond the spec's single worked table and
the one T1 test case. Script swept every subset of an 11-day window against a
range of `todayIndex` values, checking `!(atRisk && currentStreak===0)` and
`longestStreak >= currentStreak` on each:

- **Realistic sweep** (daySets that respect "nothing logged in the future," the
  only shape the real service can ever produce): 14,334 (daySet, todayIndex)
  pairs — **0 violations**.
- **Adversarial sweep** (daySets deliberately including days *after*
  `todayIndex` — a shape the real system cannot produce, since `logCompletion`
  always stamps `dayIndex(now)` and `today` only advances, but worth trying to
  break anyway): 22,528 pairs — **0 violations**. Traced algebraically why:
  `atRisk` being true requires `todayIndex-1 ∈ daySet`, which forces
  `last ≥ todayIndex-1`, which forces `currentStreak`'s early-return-0 branch
  (`last < todayIndex-1`) to be false — so `atRisk` and `currentStreak===0` are
  mutually exclusive **by construction**, regardless of what else is in the
  set. The guarantee is structural, not merely empirical.
- **Scenario walk** (single day, 2-day run, 11-day run, run with an internal
  gap, multiple disjoint runs — each evaluated at day N, N+1, N+2, N+3, N+10,
  N+100): 30 pairs — **0 violations**, and the state transitions match
  `05-arch.md`'s case table exactly (healthy → at-risk → broken, with longest
  frozen at the pre-break value in every shape).

Total: **36,892 checked, 0 violations.**

**Probe B — client-authority.** Grepped the full repo for any HTTP/route/server
code (`http.createServer`, `express`, `req.body`/`query`/`params`, etc.) —
**none exists anywhere in this repo**. `now` is the only clock-shaped
parameter on any exported function, and every occurrence defaults to
`Date.now()`. Since there is no route at all, there is categorically no
client-suppliable date path — a stronger guarantee than "the route doesn't
forward it," because there is no route.

One documentation-precision note (not a safety violation): `06-impl.md` claims
"every `Date.now()` occurrence in `src/` is a default-parameter declaration,"
verified by grep. That's true but the grep pattern was narrower than the
claim — it would miss `new Date()` (no args), which also reads the real
clock and appears twice: `habits.js:45` (`createdAt`) and `audit.js:16` (`at`).
I confirmed both are dead-end metadata — grepped for read sites and found
`createdAt` is written once and never read back anywhere, and `computeView`
never touches `habit.createdAt` or event `.at`. Neither feeds the streak/day-
cutoff math, so §1 is not affected — just flagging that the engineer's
self-check was less exhaustive than its own wording implied.

### §2 — A streak is never silently zeroed; longest never decreases

**Probe** — end-to-end through the real service layer (`habits.js`, not the
pure functions), three separate runs separated by 3-day gaps: a 4-day run, a
**shorter** 2-day run, then a **longer** 6-day run.

- After every break, `currentStreak` was exactly `0` (3/3 breaks).
- `longestStreak` was monotonic non-decreasing across all 15 recorded steps of
  the sequence (checked programmatically, not just spot-checked).
- Critically, `longestStreak` **stayed at 4** after the shorter 2-day run
  broke (proving a short run can't accidentally lower it), then **updated to
  6** once the third run genuinely exceeded the old best — proving the value
  is recomputed fresh on every read, not a stored counter that could get
  stuck. Source-level confirmation: the `habits` Map's record shape
  (`{habitId, userId, name, createdAt}`) has no `longestStreak` field at all;
  it only ever comes from `streak.js`'s `longestStreak(daySet)`.

### §3 — No guilt / loss-aversion mechanics

**Probe** — grepped `src/`, `test/`, `scripts/` for leaderboard, streak-freeze/
repair, points/levels/badges/avatars, and notification/push/reminder
mechanics: **no matches** (the only "push" hits are `Array.prototype.push`
calls, unrelated). Also grepped for a returned `"broken"` string or `state`
field: **none** — `"broken"` appears only in code comments and test names
(developer-facing), never in anything the service returns. Consistent with
the spec: the service returns only raw booleans/integers/ISO strings; all
reframing copy is deferred to a not-yet-built frontend.

### §4 — A user only ever affects their own data

**Probe**, extending T6: rejected cross-user `logCompletion` against a
**real-but-foreign** habitId vs. a **fully fake** habitId — both returned
`null`, and the two results were byte-identical (`JSON.stringify` equal),
so a would-be attacker gets **no existence-leak signal** distinguishing "not
yours" from "doesn't exist." u1's habit view and audit-event count were
byte-identical before and after u2's rejected attempts, and u2 accrued **zero**
audit events from the attempt (no side-channel record even of the attempt
itself). Also checked `userId` is strictly case-sensitive (`"U1"` is not
treated as `"u1"`) — no accidental case-folding widens ownership. Source
confirms the ownership check (`habit.userId !== userId`) runs before the
completion `Set` is ever read or written.

### §5 — Logging is idempotent per day

**Probe**, extending T5: **triple** same-day logging (not just double) — 1st
call `changed:true`, 2nd and 3rd both `changed:false`, `currentStreak` steady
at 1 across all three, and **exactly one** `habit.completion_logged` audit
event for the day. Millisecond-precision day-boundary probe: logged at
`23:59:59.999Z`, then again 1ms later at `00:00:00.000Z` the next UTC day —
correctly registers as a **new** day (`changed:true`, streak 1→2); a
follow-up log at `23:59:59.999Z` of that new day is correctly idempotent
(`changed:false`, streak stays 2). Confirms the cutoff is exact UTC midnight,
not a rounded or fuzzy window.

### §6 — No sensitive content in audit/telemetry

**Probe**, extending T7: five distinctive habit names, including Unicode
(`喝水八杯`), a name that imitates a habitId (`"habit_1-lookalike-name"`), and
a name that imitates a metadata key (`"dayIndex-and-currentStreak-lookalike"`).
Logged each (first log + an idempotent same-day re-log + an at-risk-clearing
log the next day), then dumped **every** audit event for the user
(`JSON.stringify`, no filtering) and searched for each name in full and by
prefix.

First pass reported a hit — turned out to be a false positive in my own probe:
the prefix `"dayIndex"` (from the metadata-key-lookalike name) matched the
**legitimate JSON key** `"dayIndex": 20574` in a `completion_logged` event,
not the name's value. Verified directly (`dump.includes(fullName)` → `false`;
inspected the raw event: `{habitId, dayIndex: 20574, currentStreak,
longestStreak}`, a plain integer, no string trace of the name). Corrected the
probe to exclude legitimate key-name collisions and re-ran: **zero** name
leakage, full or partial, across all 5 names. Event count was exactly 15 (5
`habit.created` + 10 `habit.completion_logged` — the 5 idempotent re-logs
correctly emitted nothing), and `metadata` keys were exactly `{habitId}` /
`{habitId, dayIndex, currentStreak, longestStreak}` on every single event,
confirmed programmatically, not spot-checked.

## 3. Additional finding (beyond the six invariants)

Probing "try to break it" surfaced a real, verified gap outside the scope of
the six named invariants but worth recording plainly rather than omitting.

**Unvalidated `now` → permanent data corruption + cascading read failure.**

- `dayIndex()`/`isoDateUTC()` never check that `now` produces a finite number.
  Passing an invalid `Date` (`new Date("garbage")`, `.getTime()` → `NaN`) to
  `logCompletion` does **not** throw the documented `TypeError`. Instead:
  `days.add(NaN)` succeeds silently (partial mutation, before any guard), and
  the function only fails later, inside `isoDateUTC`'s `new
  Date(NaN).toISOString()`, with an **undocumented `RangeError: Invalid time
  value`** — unlike the other two guards in this same function, which throw
  *before* touching the `Set`.
- The corruption is **permanent** (in-memory, until process restart): I
  confirmed a *subsequent* call with a perfectly valid `now` against the same
  habit **still throws** — the habit is permanently unreadable.
- **Blast radius is wider than one habit.** `listHabits(userId)` builds views
  for all of a user's habits in one loop; I confirmed a second, untouched
  habit (`a2`) is fine in isolation (direct `logCompletion` on it works), but
  `listHabits(userA)` throws and returns **nothing** — one corrupted habit
  denies that user visibility into *all* their other, healthy habits.
- **Scope-limiting, confirmed by test:** cross-user exploitation is **not**
  possible. The §4 ownership check runs before `dayIndex(now)` is ever
  called, so user B attempting this against user A's habit is cleanly
  rejected (`null`, no mutation) — this is strictly self-inflicted.
- **Live reachability today: none.** Per §1 above, there is no HTTP route or
  any client-facing entry point anywhere in this repo, so `now` can only be
  supplied by trusted same-process code — no shipped path (tests, demo
  script) does this. It does not violate §1 ("never client-supplied") because
  there is categorically no client path yet.
- **Why it's worth flagging now anyway:** the spec's §1 safety argument rests
  entirely on "no route exists yet." The moment a future slice adds an HTTP
  layer, a common, easy mistake — forwarding a client date field via `new
  Date(req.body.date)` into `now` without checking `.getTime()` — would let
  any caller permanently corrupt and DoS their own habit list with one
  malformed request. **Recommend:** add a finiteness guard on `dayIndex()`'s
  result (`Number.isFinite`), throwing `TypeError` consistent with the
  existing guards, *before* any `Set` mutation — ideally landed before any
  HTTP/adapter slice is built on this service, not as a reaction to an
  incident.

Two minor, non-blocking notes are folded into §1 and are not repeated here:
the `Date.now()`-only grep in `06-impl.md` (documentation precision) and
whitespace-only strings passing the "empty/non-string" guard (matches the
spec's literal contract, confirmed intentional, not a bug).

**PASS.** Recommend proceeding to Security & Privacy.
