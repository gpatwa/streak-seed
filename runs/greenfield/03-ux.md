# Feature Spec — StreakKeeper (MVP slice)

> Owner: UX Researcher Agent · Status: ready for UI · Source: `02-prd.md` · Resolves: the blocking at-risk/broken-streak tone question

## Scope note

This slice ships as a headless, dependency-free, in-memory Node service — no screens yet. Every "state" below is a computed data shape (booleans, integers, ISO dates) the service returns, not a layout. Copy, color, and pixel layout belong to the UI Designer; this spec fixes what each state *means* and what it should *feel like*, precisely enough that neither of them has to invent the user or the logic.

## Resolved: at-risk & broken-streak semantics (the blocking decision)

**At-risk.** True exactly when a habit was completed yesterday and has not yet been completed today; false in every other case. Critically, the *current streak number does not drop* the moment the calendar rolls to a new day — it keeps showing yesterday's intact count, with `atRisk: true` layered on top as a fact, not a threat. Zeroing the display before the user has even had a chance to log today would itself be a small punitive act — exactly what this product is defined against.
**Tone — at-risk:** a calm, present-tense statement of fact ("here's where you stand today"), not a countdown or a call to act. No urgency language, no loss-aversion framing, no color-only alarm signal.

**Broken streak.** A streak breaks once a full calendar day has elapsed with zero completions — i.e., yesterday was also not completed, the one-day at-risk grace window has closed, and current streak resets to `0`. Longest streak is untouched and stays visible.
**Tone — broken:** matter-of-fact and backward-permitting. States that the gap happened, with no "streak lost," no negative number, and no red/danger-only styling. The longest-streak value stays on screen as proof the history is real and wasn't erased — today is an ordinary, ungated chance to start again, not a penalty to climb out of.

Both states are read-outs, never verdicts. The mirror shows the day; it doesn't grade it.

## 1. Personas

**The Bounced Tracker — lead and only persona this slice needs.** Non-goals rule out social/accountability features, so there's no second role to design for (no friend viewing your progress, no coach/admin) — one user, one honest mirror.

- **Who:** has installed and abandoned 2+ habit trackers, and specifically names gamification or guilt — not missing features, not bad UI — as why the last one got deleted.
- **Moment A — re-trying:** just walked away from (or is about to walk away from) a tracker after a punitive reaction to a missed day — a reset chain, a dead avatar, a guilt-trip push — and is deciding whether it's worth risking one more app.
- **Moment B — steady state:** the morning after a missed day, opening the app wanting an honest, non-judgmental read on where they actually stand. This is the moment the at-risk and broken-streak states exist to serve.
- **Wants:** an accurate reflection of consistency, not motivation manufactured through fear.
- **Distrusts:** streak resets framed as loss, and anything that smells like it could later monetize "protecting" a streak — the persona doesn't yet know the product's non-goals rule this out, so the early states carry the burden of proof.
- **Slice success:** sees a missed day reflected plainly, sees their real history preserved, doesn't feel punished, keeps using it instead of deleting it — day one of not repeating the bounce pattern.

## 2. Primary journey — happy path

Each step is a concrete user action → the concrete system response (computed data, not screen).

1. **User opens their habit list.** → Service returns, per habit: `{ currentStreak, longestStreak, atRisk, lastCompletedDate }`, computed as of "today." Nothing is flagged at-risk unless it meets the exact definition above.
2. **User logs "Meditate" complete for today — first time ever.** → `currentStreak: 0→1`, `longestStreak: 0→1`, `atRisk: false`, `lastCompletedDate: today`.
3. **Next day, user opens the app before logging anything.** → "Meditate" was completed yesterday, not yet today: `atRisk: true`, `currentStreak` still reads `1` — intact and in-question, not already lost.
4. **User logs "Meditate" complete for today.** → `atRisk` clears to `false` immediately, `currentStreak: 1→2`, `longestStreak` recalculated as `max(longest, current) = 2`.
5. **Pattern repeats over subsequent days.** → Each on-time log increments `currentStreak` and raises `longestStreak` whenever current overtakes it; `longestStreak` never decreases, by definition.
6. **User checks in at any later point.** → Sees both numbers side by side: a truthful record of consistency (`longestStreak`) that survives any future lapse, and a truthful record of right now (`currentStreak`).

## 3. Alternate journeys

**Logging a second habit.** User logs "Read" while "Meditate" is mid-streak. Each habit's `currentStreak` / `longestStreak` / `atRisk` is computed and stored independently — no combined score, no aggregate "2/3 done today" completion percentage, no cross-habit ranking. Per non-goals, there is no comparison here, even against the user's own other habits — every habit is its own mirror.

**Viewing after a lapse.** User opens the app having missed a day entirely — the exact scenario the PRD's problem statement is built around. → That habit now reads `currentStreak: 0`, `longestStreak: <unchanged>`, `atRisk: false`. No punitive field, flag, or copy exists anywhere in this state (no `streakLost`, no negative count). The habit is exactly as loggable today as on any other day.

## 4. Edge cases & failure modes

**Day boundary — "what counts as today."** The crux of the whole feature. `currentStreak`, `atRisk`, and the broken-streak reset must all derive from one single, consistently applied day-boundary rule — a mismatch (e.g., one computed in local time, another in UTC) produces contradictory states, like a habit that is simultaneously `atRisk` and already reset. This slice has no user accounts or stored timezone, so recommend: **the boundary is UTC midnight**, applied uniformly, server-side, and never client-supplied — a client must not be able to pass "which day" a completion counts toward, or a log could be spoofed across the boundary. This is a deliberate simplification for a single-process prototype; real per-user timezone correctness is out of scope for this slice and should be flagged as a known follow-on, not silently assumed away.

**First-ever log.** `currentStreak: 0→1`, `longestStreak: 0→1`, `atRisk` stays `false` — there is no "yesterday" to be at risk relative to. Goes straight from empty to active; no at-risk flash in between.

**A streak of exactly 1.** No minimum-length threshold anywhere in the logic or the tone. A 1-day streak is exactly as eligible for `atRisk` tomorrow, and exactly as eligible to break the day after, as a 200-day streak — and reads with the same calm tone regardless of length. Easy bug to introduce by unconscious analogy to other apps: don't gate `atRisk` on streak length.

**Broken streak (gap ≥ 1 day).** Trigger and reset behavior are defined in the Resolved section above. One added precision point: once broken, `atRisk` must be `false`, not stuck `true` — broken is its own terminal state, not a more-urgent flavor of at-risk.

**Logging the same habit twice in one day.** Idempotent. A second log call on an already-completed-today habit is a no-op against the streak math — no double increment, no double-counted `longestStreak` bump, `lastCompletedDate` unchanged. Not an error: the user didn't do anything wrong by tapping twice, so nothing about the response should read as a correction or failure.

**Many habits at once.** Every habit's three values are computed independently, with the identical day-boundary rule applied to all of them — two habits logged at different times "today" must both unambiguously count as today. No shared state and no aggregate view across habits.

## 5. Accessibility

Concrete behaviors the eventual UI must satisfy, and what this service's data contract needs to expose to make them possible:

- **Keyboard.** The log-completion control must be a standard actionable element operable via Enter/Space — no hover-only, drag-only, or press-and-hold-to-confirm gesture. (Press-and-hold-to-confirm is itself a small gamified friction pattern, worth ruling out on tone grounds as much as access grounds.)
- **Screen reader semantics.** Streak counts are exposed as plain text/accessible names, never baked only into an icon, image, or flame glyph — an accessible name must at minimum carry the habit name and both streak numbers as readable text. The at-risk fact is announced as text conveying, at minimum, that yesterday was completed and today is not yet — never by color alone. If a live region announces `atRisk` clearing after a log, it fires once, calmly — not as a celebratory or repeating alert.
- **Contrast.** Any future state-color coding meets WCAG AA against its background and is always paired with a text or icon cue — color-only signaling both fails colorblind users and is precisely the "scoreboard-red" cue the tone stance argues against.
- **No motion or animation that gamifies.** No count-up number animations, no confetti or celebration effects on logging, no progress-bar fills, no flame/icon growth, no shake or pulse to manufacture urgency on at-risk, no "shatter" or "break" animation on a broken streak. State changes render as immediate, static updates. This is a hard constraint from the anti-guilt stance, not a nice-to-have — animated urgency is the mechanism gamified trackers use to manufacture loss-aversion, so its absence is load-bearing, not decorative restraint.
- **Data-contract implication.** The service must expose raw semantic values — booleans, integers, ISO dates — not pre-rendered, tone-laden strings or emoji. Baking copy into the data layer would take these accessibility and tone decisions out of the UI Designer's hands.

## 6. Empty / loading / error states

| State | Trigger | Name | Intended tone |
|---|---|---|---|
| No habits yet | Fresh instance, no habits configured | Empty | Neutral, inviting — absence, not failure. Habit creation isn't a feature of this slice per PRD scope, so this mostly matters for a fresh seed/test run. |
| Habit, no completions | Habit exists, zero logs | Not started | Neutral, forward-looking. `currentStreak: 0` here must not read or look like a broken streak — same number, different meaning, and must not share broken's visual/tonal treatment. |
| At-risk | Completed yesterday, not yet today | At risk | Calm, factual, present-tense. See Resolved section. |
| Broken streak | Gap ≥ 1 day since last completion | Broken | Matter-of-fact, backward-permitting, longest streak kept visible. See Resolved section. |
| Loading | N/A for this slice | — | The service is synchronous and in-memory — every response is immediate, so no loading state exists at this layer. A future networked frontend will need its own loading treatment; flagged here so it isn't silently forgotten later. |
| Error | Invalid/unknown habit id, malformed request | Error | Neutral and technical — a system fault, not a behavioral read-out. Must not borrow the gentle "mirror" tone reserved for legitimate at-risk/broken states, and must not be alarming either — system errors and honest behavioral state should never be visually or verbally confused. |
